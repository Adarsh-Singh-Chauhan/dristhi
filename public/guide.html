01 / USER WORKSPACE

Inspect a public claim.

Open the user workspace and choose Overview. Submit only public material or content you are authorised to review. Keep the original wording, platform and source reference intact.

STEP 01

Paste the message

Enter the claim or post text. Avoid passwords, private group messages and personal data.

STEP 02

Add context

Select WhatsApp, Telegram, Instagram, Facebook, X, web or other. Add a public source URL when available.

STEP 03

Run analysis

Select Analyse message. Review each matched indicator and its explanation instead of relying on the score alone.

Important: Review priority is not a probability that a claim is false. High score ≠ false, and low score ≠ true. Always verify the original circular, publication date, source and surrounding context.
02 / EVIDENCE CASE FILES

Turn a concern into a traceable case.

When a claim needs a formal review, create a case from the analysis result. The purpose is to preserve the claim and its source—not to publish an accusation.

Submit a case

  1. Run an analysis first.
  2. Choose Create case file in the result panel.
  3. Enter a neutral case title and category.
  4. Add why the claim needs review and a source URL if known.
  5. Submit, then open My case files to see the case ID and status.

Follow the review

  1. Open My case files from the workspace sidebar.
  2. Search or filter by status.
  3. Open a case to see the review timeline.
  4. Read the evidence summary and cited sources added by the reviewer.
  5. Check whether the status is still pending or has a sourced outcome.
StatusMeaning
ReceivedSubmitted; no conclusion has been reached.
Under reviewA human reviewer is examining context and source evidence.
Verified falseA reviewer recorded why the claim is false or manipulated and attached source evidence.
Supported by sourcesThe submitted claim is supported by the cited evidence.
Misleading contextThe material may be genuine, but its date, place, framing or context changes its meaning.
Insufficient evidenceEvidence does not justify a reliable conclusion.
ClosedReview was closed without a stronger public conclusion.
The three conclusive outcomes—Verified false, Supported by sources and Misleading context—require a written evidence summary and at least one HTTP/HTTPS source URL in the current API. The reviewer must still assess the source quality and relevance.
03 / SUPERADMIN CONTROL ROOM

Review evidence. Record the reasoning.

The real Superadmin console is protected by a server-side role check. Never use public demo credentials to sign in to production. The demo Superadmin role is only a browser simulation.

STEP 01

Open the case desk

Read the original claim, reporter context, submitted source and analysis summary.

STEP 02

Verify independently

Open primary sources, compare publication dates, and seek independent corroboration or original media.

STEP 03

Write the decision

Add evidence summary, source URLs, reviewer notes and the appropriate status. The API records privileged changes in the audit log.

Operations modules

  • Evidence case desk and review status
  • SOS queue and reviewer notes
  • Public IP/domain threat-indicator registry
  • In-app notice publisher
  • Read-only user account overview
  • Audit trail for privileged actions

Threat indicator rules

  • Add only public IP/domain indicators you are authorised to investigate.
  • Include a source/provenance reference and analyst note.
  • Private, local and reserved IP ranges are rejected by the current API.
  • An IP is not a person; GeoIP is approximate network metadata.
04 / ALERTS & SOS

Safety requests and in-app notifications.

Users can manage trusted-contact references and submit a request for internal review. Location sharing is optional and, when enabled, is a one-time browser GPS snapshot attached to that SOS report.

To submit an SOS request

  1. Open Alerts & SOS and sign in.
  2. Enter a clear title and factual incident details.
  3. Add a source URL if the issue relates to a public notice, link or account.
  4. Choose whether to share one-time GPS for this request.
  5. Submit and follow the status from the same page.

What happens next?

The request is stored in the internal review queue when persistent storage is configured. A Superadmin may add notes and update status. The system does not automatically message contacts, call emergency services or dispatch responders.

Emergency: DRISHTI SOS is not a replacement for local emergency services. In an immediate emergency, contact the appropriate emergency number directly.
05 / PHONE EXPERIENCE

Use DRISHTI on Android or iPhone.

The mobile experience is an installable Progressive Web App (PWA), not a native Play Store APK or App Store application.

Android · Chrome

  1. Open the DRISHTI workspace in Chrome over HTTPS.
  2. Tap Install app if the prompt appears.
  3. Otherwise open the ⋮ menu and choose Install app or Add to Home screen.
  4. Launch DRISHTI from its home-screen icon.

iPhone · Safari

  1. Open the DRISHTI workspace in Safari.
  2. Tap the Share icon.
  3. Choose Add to Home Screen.
  4. Confirm and launch the saved icon.

07 / DETECTION METHODOLOGY

Understand what the analyser actually detects.

The production baseline is deterministic and explainable. It currently checks a limited set of text patterns and common URL shorteners.

Current rule signals

  • Urgency language and forwarding pressure
  • Authority claims without an in-text source
  • Forward-chain markers
  • Panic or threat wording
  • Selected common shortened URLs
  • Unusually high capitalisation and repeated punctuation

Recommended human checks

  • Find the earliest version of the claim.
  • Open an official primary source where relevant.
  • Compare date, location and surrounding context.
  • Look for independent corroboration.
  • Check original image/video and media provenance.
  • Record uncertainty when sources disagree.
08 / CAPABILITIES & LIMITATIONS

Current prototype boundaries.

Implemented in the repository

  • Responsive user workspace and PWA shell
  • Rule-based text-signal analyser
  • Analysis history UI and case-file APIs/UI
  • Superadmin case desk and evidence rules
  • Alerts, trusted contacts and SOS workflow
  • Public IP/domain IOC registry and audit trail
  • Browser-only 40-minute role-based demo

Not active in production today

  • Trained mBERT or XLM-RoBERTa model
  • Live X, Reddit or Telegram collection
  • NetworkX bot/campaign detection
  • Gemini threat Q&A assistant
  • Image, audio or video deepfake forensics
  • Automatic source verification or takedowns
The Vercel project currently has no production DATABASE_URL configured. The website and public demo can be explored, but production registration, sign-in, persistent history/cases, SOS and real Superadmin operations need PostgreSQL setup first. Never use the public demo password for a real account.
